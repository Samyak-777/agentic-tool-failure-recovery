## 3. How to Run Evaluations

All evaluations (CARE agent or vanilla Baseline agent, on Gemini cloud or local Qwen via Ollama) are driven by the unified CLI script:
📁 `ToolMaze/evaluation/scripts/run_eval_care.py`

### CLI Parameter Reference Table

| Flag | Allowed Values | Default | Purpose |
| :--- | :--- | :--- | :--- |
| `--config` | Path to YAML | `evaluation/configs/gemini_eval_config_c1.yaml` | Base YAML configuration file |
| `--agent-type` | `care`, `baseline` | `care` | Selects either the 7-Layer CARE agent or standard baseline agent |
| `--backend` | `gemini`, `ollama`, `vllm` | `gemini` | Selects LLM serving endpoint |
| `--category` | `c1`, `c2`, `c3`, `c4` | Auto / from config | Selects DAG complexity category |
| `--model` | e.g., `gemini-3.8-flash`, `qwen3:8b` | From config | Overrides model name without editing YAML |
| `--modes` | `P0`, `P1`, `P2`, `P3`, `P4` | All modes | Filter specific perturbation modes |
| `--task-id` | e.g. `C1_task_001` | `None` | Run only one specific task (great for quick debugging) |
| `--limit` | Integer | `None` | Limit number of tasks to evaluate |
| `--offset` | Integer | `0` | Offset into task list for chunked runs |
| `--max-workers`| Integer | `2` | Number of parallel evaluation threads |
| `--run-id` | String | Auto-generated timestamp | **Folder name** inside `evaluation/experiment_records/` |
| `--no-resume` | Flag | `False` | Forces re-running tasks instead of loading cached inferences |
| `--output-dir` | Path | `evaluation/results` | Custom results output folder |
| `--env-file` | Path | Auto-detect | Custom path to `.env` file with Gemini keys |

To test a single task (e.g. `C1_task_001` in Mode P1) with CARE:

## 6. Where Outputs are Stored & How to Read Them

### 1. Telemetry Experiment Records (`ToolMaze/evaluation/experiment_records/<run_id>/`)
This is the primary persistent output updated by Mrunmayee's latest commit:
* **`run_manifest.json`**: Records the exact git commit hash, launch arguments, config parameters, and start time.
* **`events.jsonl`**: Real-time event stream logging tool calls, validation passes/failures, diagnoses, and recovery decisions.
* **`run_summary.json`**: High-level metrics for the run (total tasks, passed tasks, TSR per perturbation mode).
* **`task_records/<task_id>_<mode>.json`**: Detailed JSON for every single task containing:
  * `"task_definition"`: Full original task specification (user intent, initial inputs, ground-truth paths).
  * `"tool_calls"`: Complete list of executed tool calls and returned payloads.
  * `"validations"`: Semantic Output Validator (SOV) checks.
  * `"recovery_events"`: Directives issued (RETRY, REROUTE, ABORT).
  * `"judgement"`: Final pass/fail verdict from the Judge System.

### 2. High-Level Metrics & Traces (`ToolMaze/evaluation/results/<model>-<agent_type>/`)
* **`metrics/metrics_report_<timestamp>.json`**: Contains the final aggregated TSR, PRR, and RC numbers formatted for publication tables.
* **`inferences/`**: Formatted conversation history with system prompts and tool call arguments.
* **`evaluations/`**: Judge evaluation rationales.

## 7. Important Tips & Troubleshooting FAQ

1. **How does Multi-Key API Rotation work?**
   * `SharedKeyPool` inside `run_eval_care.py` automatically scans environment variables starting with `GEMINI_API_KEY` as well as known secrets files (`/mnt/data/toolmaze_project/secrets/gemini_env`).
   * It enforces a thread-safe delay between calls (1.0s) and rotates across available keys.
   * If a `429 RESOURCE_EXHAUSTED` error occurs on one key, it automatically sleeps with exponential backoff and rotates to the next key without crashing the evaluation.

2. **Why use `--max-workers 2` instead of 4 or 8?**
   * Free-tier Gemini keys have a 15 requests-per-minute (RPM) quota. 2 workers rotating across 4 keys averages ~3–4 calls per minute per key, staying safely under Google's rate limits.
   * On Ollama, 2 workers maximize GPU compute throughput on the 24GB Titan RTX without thrashing KV cache memory.

3. **What does `--no-resume` do?**
   * By default, `run_eval_care.py` checks if a task's inference already exists in `evaluation/results/` to save tokens.
   * `--no-resume` ignores previous inferences and forces a fresh run from scratch. Use `--no-resume` when benchmarking code changes.

4. **Where to see Baseline vs CARE comparison?**
